# /setup — decidir o modo, ler, inferir, perguntar, gravar, devolver

Dono **único** de `.claude/ship/setup.md`: como este time trabalha — branch, commit, PR, rastreamento, cards, ponteiros de infra e guidelines. Todo alvo e modificador começa por aqui. **Resolve como o time trabalha e devolve**; não cria card nem branch. Seis passos, nesta ordem:

1. **Decidir o modo — do time ou só meu, uma vez, para os cinco arquivos** (`setup`, `jira`, `infra`, `deploy`, `patterns`). `setup.md` existe → **time** (versionado, igual para quem clona); só `setup.local.md` → **só meu** (repo de um time que não usa este processo; fora do git; o do time vence se os dois existem). Nenhum: `.claude/` não ignorado → time; ignorado → **pergunte** — pode ser o time dizendo que processo de agente não entra ali (org alheia ⇒ "só meu" primeiro). Time com `.claude/` ignorado → proponha corrigir o `.gitignore` (excluir os filhos e reincluir a pasta do processo; negação sob pasta excluída não reinclui), confirmando antes.
2. **Ler — explicitamente, a cada invocação.** "Já está no contexto" não é leitura. Seis seções completas → passo 6, sem ir ao GitHub reconfirmar; campo faltando → só o que falta, com o default. Lido **sob demanda** por quem usa — nunca via `CLAUDE.md`, `.claude/rules/` ou memória: carregado em toda sessão é o problema que este arquivo resolve.
3. **Inferir antes de perguntar, citando a fonte.** Convenção de commit e posição da key pelo histórico; PR ou push, modo de branch e caixa do nome pelos PRs mergeados (várias keys no título ⇒ lote); estratégia de merge e proteção de branch pelo GitHub (uma só habilitada ⇒ é ela; sem permissão → diga, não assuma); quem aprova pelo `CODEOWNERS`; template de PR pela pasta `.github/`; o que o `CONTRIBUTING` confirma ou contradiz (contradição é pergunta); rastreamento pelo board do `/jira` ou pela pasta `obra/`. Inferência **ordena** as opções; quem decide é o usuário.
4. **Perguntar — uma vez, isolada, no máximo três.** Trabalho (direto na integração · branch por card · branch acumula cards) · Aprovação (a própria skill · pessoa/time — só com PR) · Merge (só se o GitHub habilita mais de uma) · Rastreamento (só se a inferência não decidiu). Com candidato provável, a pergunta **confirma**, não abre menu. Não pergunte o que tem default: nome da branch, key do card, DoD, destino do card novo, atribuir a, infra, guidelines — tudo editável depois por `/setup <seção>`.
5. **Validar e gravar.** Consistência: `direto na integração` ⇒ `Abre PR: não` ⇒ aprovação, merge e template `—`; branch aceita `Abre PR: não` (sobe por push); sem Jira, os campos de card ficam `—`; contradição não grava. Arquivo do modo, seções: Branch (trabalho, nome) · Commit (convenção, key do card) · PR (abre, aprovação, merge, template) · Jira (rastreamento, idioma dos cards, DoD, destino do card novo, atribuir a, estrutura) · Infra (mapa, processo, conta) · Guidelines. Aqui mora **política**; fato tem outro dono — topologia e branches no `deploy.md`, cards de um lote nos commits, board no `/jira`, colunas no `jira.md`, segredos no `infra.md`, padrões de código em `.claude/patterns.md`. Time → avise que é versionado e entra no commit de quem chamou.
6. **Devolver** branch (modo, nome), commit (convenção, key), PR (abre, aprovação, merge, template), Jira (rastreamento, idioma, DoD, destino, atribuir), infra, guidelines, origem e arquivo. Pedido de sessão ("hoje quero branch") vale para a invocação e não reescreve nada; só `/setup <seção>` reescreve — mostra a seção, pergunta o novo valor, valida e regrava **só ela**. Vazio num repo sem arquivo = projeto novo: roda tudo e oferece `/infra` e `/jira`, sem invocar.
