# /homolog — descobrir, garantir a PR, gate de QA, revisar, mergear ou rejeitar, publicar, devolver

O terceiro **alvo**: o estado pedido é **o trabalho no ar em homolog, funcionando**. É um **gate, não uma esteira**: PR inaceitável é devolvida, e "mergeado" não é "entregue". `<produção>` é o `/prod`. Sete passos, nesta ordem, cada um provado antes do seguinte:

1. **Descobrir — board, convenções, ambiente, objetivo.** Composição primeiro (`repro → card → alvo`; modificador e skill de fora rodam antes; `/prod` vence — delegue; `/work` e `/pull-request` perdem). `/jira` e `/setup` (`Abre PR`, `Aprovação`, `Merge`) via **Skill tool, a cada invocação**; `<integração>` e o ambiente em `infra/SKILL.md` § Deploy — `dev` → homolog é só o padrão, o uso decide, não o nome. Sem homolog (branch única: commit → push → `main` → prod) esta skill não trabalha: sugira `/prod`, sem invocar. Objetivo: vazio = tudo que está pronto; PR ou key = preferência de ordem. Diagnóstico publicado antes de agir: `pr`, `integrado` (PR mergeada e branch apagada), ambiente (run verde cobrindo o HEAD da integração, configurado, validado); tudo fechado → gap zero.
2. **Garantir a PR.** PR faltando ou trabalho atrás → `Skill(skill: "pull-request")` fecha; nunca "rode antes". Sem PR por convenção (`Abre PR: não`) → o que se revisa são os commits ainda não verificados na integração. PRs abertas → **uma por vez**.
3. **Gate de QA — o que entra tem de ter passado.** Cards da PR = título, `## Cards` e commits. Artefato em `obra/12-done/` com `obra/10-run-test/` 100% → confia, só review; QA ausente, ambígua ou falha → review com front-test do `## Como testar` de cada card; artefato ainda em `obra/07-todo/` → o commit não fechou: feche na branch da PR (`Skill(skill: "work")`) e pushe, ou rejeite; sem card → pergunte; ledger de follow-ups com item `ABERTO` → rejeite.
4. **Revisar — o diff, sempre você.** Arquivo a arquivo: bugs, edge cases, padrões do projeto, segurança, performance, código morto, "faz o que o card pede"; escopo é o diff. Conserto pontual é in-place com re-review; "consertar" que vira reimplementar é rejeição, assim como abordagem errada, não fazer o que o card pede ou ~3 rodadas sem convergir. Achado fora do escopo: ponta que o dev tinha como ver → rejeita; só o review enxerga → **A** bug (prova: reprodução) · **B** furo (frase **verbatim** de doc/UC/setup + ausência no código + consequência material) · **C** melhoria (opinião, só relatório); intencional documentado não é achado — registrado em `obra/09-code-review/` § Achados, **nunca card**. Excedente (o card não pediu): separável → sai por request-changes, registrado; entrelaçado → re-split; mexer no arquivo que a mudança toca não é excedente.
5. **Mergear — ou rejeitar.** Aprovar registra o review na PR (PR sua → comentário); `Aprovação: <pessoa>` → o merge espera o aprovado dela, gap aberto. Branch atrás ou conflitante → atualiza com a integração, re-revisa, pusha. Merge pela estratégia do setup; branch apagada **remota e local** (recusa de apagar → pare). Depois: `/jira` § Sincronizar (**integrado**); `obra/13-ship/` com o merge, commitado e pushado com paths explícitos. Rejeitar: request-changes com o quê, por quê e o que muda; nada mergeado nem apagado; `/jira` § Sincronizar (**devolvido ao dev**); artefato → `obra/08-implementation/`, `status: rework`.
6. **Publicar, configurar, validar — e só então o Jira.** `Skill(skill: "deploy", args: "homolog")` — run verde, infra configurada, atualização validada em live. Validado → `/jira` § Sincronizar, etapa **no ar em homolog**, em cada card que subiu. Passo aberto volta com o motivo; o alvo **não** é declarado atingido e o card não muda.
7. **Devolver.** Estágios (antes × agora), PRs (mergeada ou rejeitada), run, configuração, validação, cards, achados (nenhum card criado — abra com `/card`); próximo: `/prod`.
